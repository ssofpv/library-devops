Правила внесения изменений
## 1. Общий порядок работы

Все результаты проекта хранятся в одном Git-репозитории.

Каждая новая функция выполняется в следующем порядке:

1. Создать Issue с описанием задачи и условиями готовности.
2. Обновить локальную ветку main.
3. Создать отдельную рабочую ветку.
4. Реализовать изменение.
5. Добавить или обновить необходимые тесты и документацию.
6. Выполнить обязательные локальные проверки.
7. Создать осмысленные коммиты и отправить ветку на GitHub.
8. Открыть Pull Request со ссылкой на задачу.
9. Получить проверку второго участника.
10. Исправить замечания.
11. Выполнить слияние после одобрения и успешных проверок.

## 2. Имена веток и коммитов

Для веток используются префиксы:

- feat/ — новая функция;
- fix/ — исправление ошибки;
- docs/ — изменение документации;
- chore/ — настройка инструментов проекта.

Сообщение коммита должно объяснять, что изменено.

Примеры:

- docs: add contribution rules
- feat: add author creation
- fix: reject empty author name

## 3. Проверка Pull Request

Изменения проверяет второй участник команды.

Проверяющий должен убедиться, что:

- изменение соответствует задаче;
- новое поведение проверено тестами, где это применимо;
- неправильные запросы обрабатываются;
- изменения API и схемы данных отражены в документации;
- секреты и лишние локальные файлы не добавлены;
- обязательные проверки не ослаблены.

Автор исправляет замечания в той же ветке.
После исправлений выполняются повторные проверки.

## 4. Обязательные проверки

Перед отправкой изменений автор выполняет:

- make verify — анализ кода, проверку форматирования,
  проверку настроек Django, проверку наличия необходимых
  миграций и автоматические тесты;
- git diff --cached — просмотр подготовленных к коммиту изменений;
- git diff --cached --check — проверку оформления подготовленных изменений.

Команды git diff --cached выполняются после git add.

Для автоматического исправления форматирования используется
make format. После исправлений необходимо повторить make verify.

GitHub Actions выполняет make verify на Python 3.13 и 3.14.

Перед слиянием обязательны успешные проверки и одобрение
второго участника.

## 5. Запрещённые действия

Запрещается:

- удалять тесты только ради успешного прохождения проверок;
- отключать анализаторы только ради успешного результата;
- снижать пороги качества или ослаблять CI ради слияния;
- сливать изменения с невыполненными обязательными проверками;
- добавлять в репозиторий пароли, токены и другие секреты;
- включать в main непроверенные изменения в обход Pull Request.

6. Критические файлы приёмки

К критическим файлам относятся:

- конфигурация CI;
- Makefile;
- настройки тестов;
- настройки анализаторов и форматирования;
- скрипты обязательных проверок.

Изменения этих файлов должны быть отдельно объяснены
в описании Pull Request и проверены вторым участником.

## 7. Конфигурация и локальные файлы

Настройки приложения передаются через переменные окружения.

В .env.example размещаются названия необходимых переменных
и безопасные примеры значений.

Реальные секреты и локальные файлы исключаются из Git
с помощью .gitignore.

Файлы миграций базы данных хранятся в репозитории.
