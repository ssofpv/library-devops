# Аутентификация сотрудника

Обновление закрывает требование ЛР1 от 18.09.2026. Все сотрудники имеют одинаковый
доступ к каталогу и фонду. Самостоятельная регистрация посетителей не предусмотрена.
Приложение остаётся локальным учебным проектом.

## Первый запуск

1. Подготовьте окружение и `.env` по README.
2. Выполните `make migrate`.
3. Создайте администратора: `.venv/bin/python manage.py createsuperuser`.
   Windows: `.\.venv\Scripts\python.exe manage.py createsuperuser`.
4. Запустите `make run`, откройте http://127.0.0.1:8000/accounts/login/.
5. Введите выбранные логин и пароль. Для сотрудника можно создать отдельного активного
   пользователя через `/admin/` без staff/superuser. В каталоге его права будут такими же.

Пароль задаётся интерактивно и не хранится в исходном коде, `.env.example` или Git.
Для смены пароля: `manage.py changepassword ИМЯ` соответствующим Python из `.venv`.

## Маршруты и ответы

| Запрос | Поведение |
|---|---|
| GET /accounts/login/ | Форма входа, 200 |
| POST /accounts/login/ | Логин, пароль, CSRF; успех — 302 на локальный next или / |
| Неверные данные входа | Форма с ошибкой, 200; сессия не создаётся |
| GET /accounts/logout/ | 405; GET не завершает сессию |
| POST /accounts/logout/ | CSRF обязателен; сессия удаляется, 302 на вход |
| Рабочая HTML-страница без сессии | 302 на вход с next |
| API без сессии | 403 и JSON с detail |
| GET /health/ без сессии | 200 и {"status":"ok"} |

API использует `SessionAuthentication` и `IsAuthenticated`. Код 403 без входа
для этого механизма ожидаем; это не Basic/JWT и ответ 401 здесь не обещается.
Статусы 400/404/409/405 из описания предметного API проверяются после входа.
При отсутствии или неверном CSRF изменяющий запрос с сессией получает 403.

## Проверка API

Самый быстрый способ: войти в `/accounts/login/`, затем в том же браузере открыть
`/api/authors/`, `/api/books/`, `/api/branches/`, `/api/copies/`.
Формы Django REST Framework отправляют сессию и CSRF автоматически.

Для внешнего HTTP-клиента сначала GET `/accounts/login/`, сохранить cookie,
затем POST туда же `application/x-www-form-urlencoded` с username, password и
csrfmiddlewaretoken из cookie csrftoken. Сохранить обновлённые cookie после входа:
Django меняет CSRF-токен при входе. Передавать sessionid при запросах API,
а для POST/PUT/PATCH/DELETE также заголовок `X-CSRFToken` с актуальным csrftoken.
Не передавать пароль в URL, файлах репозитория или истории команд терминала.

## Реализация и ограничения

Стандартные LoginView/LogoutView, login_required, хеширование паролей Django,
серверные сессии, HttpOnly и SameSite=Lax для sessionid. Неактивный пользователь
не может войти. Внешний адрес в next не используется для перенаправления.
Сессия ограничена сроком действия Django; cookie не задаёт постоянное хранение
между запусками браузера. Для гарантированного выхода нажимайте «Выйти».

Для публичного размещения дополнительно потребуются HTTPS, Secure-cookie,
ограничение попыток входа и настройки промышленного сервера. В ЛР1 это не реализовано.

Тесты: `config/test_auth.py`; полный запуск — `make verify`.
Исходные тесты предметной области сохранены; в их подготовку добавлен вход.
