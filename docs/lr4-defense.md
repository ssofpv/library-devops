# ЛР4: ресурсы и сценарий защиты

> После дополнительного задания production использует Nginx,
> app1 и app2. Актуальные пути, команды и результаты приведены
> в [nginx-scaling.md](nginx-scaling.md).
> Команды ниже для прежнего production с одним app являются
> историческими; основной container-check остаётся применим
> для проверки базовой конфигурации.

## 1. Размещение приложения

На ноутбуке Windows запускается Linux-ВМ library-app.
Внутри ВМ Docker Engine запускает Compose-проект library-production:

- app — Django и Gunicorn;
- db — PostgreSQL;
- postgres_data — именованный volume с данными БД.

Основной адрес: http://192.168.56.10:8000/.
Каталог развёртывания: /opt/library-container.
Порт PostgreSQL на хост не опубликован.
Прежний library-app.service остановлен и отключён от автозапуска.

Исходная БД на отдельной ВМ library-db сохранена для отката.
Новое приложение использует контейнерную PostgreSQL.

## 2. Обоснование ограничений ресурсов

Для проверенного учебного стенда использовалась ВМ с 1 vCPU
и примерно 1,9 GiB оперативной памяти.

| Сервис | Память | CPU | Обоснование |
|---|---|---|---|
| app | 512 MiB | 1,0 | Запас для Django и двух работников Gunicorn; ограничение памяти приложения |
| db | 512 MiB | 0,75 | Запас для небольшой учебной БД, соединений, миграций и восстановления; ограничение потребления CPU |

Общий предел памяти двух контейнеров — 1 GiB.
Оставшаяся память нужна ОС, Docker и другим процессам.
Временные проекты проверки и сохранённые учебные контейнеры
потребляют дополнительные ресурсы и не входят в этот расчёт.

В успешной автоматической проверке 15.10.2026 наблюдалось:
app — около 118 MiB, db — около 19 MiB.
Эти значения относятся к небольшому контрольному набору данных
и отдельным моментам измерения. Это не нагрузочный тест
и не оценка максимального потребления.

Предел 512 MiB оставляет запас относительно наблюдавшегося потребления,
но его достаточность для большей нагрузки потребует отдельной проверки.

CPU limits задают верхнюю границу потребления, а не резервируют ядра.
Сумма 1,0 + 0,75 превышает 1 vCPU ВМ: при одновременной нагрузке
контейнеры делят доступное процессорное время.
Ограничение db в 0,75 само по себе не гарантирует ресурсы приложению.

После изменения нагрузки оценивать задержки, ошибки, память
и признаки OOM. Не увеличивать лимиты без оценки ресурсов ВМ.

## 3. Запуск перед защитой

1. Включить ВМ library-app в VirtualBox.
2. Дождаться загрузки Linux и автоматического запуска контейнеров.
3. Открыть http://192.168.56.10:8000/ в браузере Windows.

Docker Desktop и SSH-туннель для основного адреса не требуются.
Автозапуск обоих контейнеров после перезагрузки проверен 15.10.2026.

Для команд подключиться по SSH.

PowerShell:

```powershell
ssh -i "$env:USERPROFILE\.ssh\library_sofia" -o IdentitiesOnly=yes sofia@192.168.56.10
```

CMD:

```cmd
ssh -i "%USERPROFILE%\.ssh\library_sofia" -o IdentitiesOnly=yes sofia@192.168.56.10
```

## 4. Показ действующего стенда

Следующие команды выполняются в Bash на library-app.
Они не меняют конфигурацию и не останавливают приложение.

```bash
cd /opt/library-container
sudo -v

prod() {
    sudo -n docker compose --env-file .env.container \
      -f compose.yaml -p library-production "$@"
}

prod ps -a
curl --max-time 10 --fail-with-body -i http://192.168.56.10:8000/health/
prod exec -T app id -u
prod exec -T db id -u
```

Ожидаются healthy у обоих сервисов, HTTP 200,
UID приложения 10001 и UID PostgreSQL 999.

Показать применённые ограничения:

```bash
sudo -n docker inspect \
  --format '{{.Name}}: memory={{.HostConfig.Memory}} nano_cpus={{.HostConfig.NanoCpus}}' \
  library-production-app-1 library-production-db-1

sudo -n docker stats --no-stream \
  library-production-app-1 library-production-db-1
```

Ожидаются Memory=536870912 у обоих контейнеров,
NanoCpus=1000000000 у app и 750000000 у db.

Полный вывод Compose config и переменные контейнеров не показывать:
они могут содержать секреты.

## 5. Демонстрация пяти проверок из задания

Автоматическую демонстрацию выполнять из /opt/library-container:

```bash
sudo -v
sudo -n make container-check DOCKER=docker
```

Проверка создаёт временные Compose-проекты, отдельные volumes,
контрольные данные и отдельный образ приложения.
Она не пересоздаёт контейнеры library-production.

| Требование защиты | Что выполняет container-check |
|---|---|
| Сборка и запуск | Собирает образ и ожидает healthy приложения и БД |
| Пользователь процесса | Проверяет UID команды и процесса PID 1 у app и db |
| Сохранение данных | Сравнивает данные после пересоздания контейнеров и замены образа |
| Корректное завершение | Проверяет код выхода 0, отсутствие OOMKilled и сообщения Gunicorn об обработке SIGTERM |
| Новый volume | Восстанавливает pg_dump в отдельный проект с новой БД и сравнивает данные |

Дополнительно проверяются HTTP 503 и переход в unhealthy
при остановке временной БД, затем восстановление healthy и HTTP 200.

Ожидаемый итог: CONTAINER_CHECK_OK и код завершения 0.
Промежуточные успешные шаги не заменяют итоговый результат.
При ошибке проверка выводит диагностику и завершается ненулевым кодом.
В конце удаляются сгенерированные проекты проверки.

Отдельная ручная демонстрация backup/restore описана в
[container-backup-restore.md](container-backup-restore.md).
Она рассчитана на учебный проект library-lr4-check
с работающими healthy app и db. Не выполнять её без проверки
этих условий и не подменять имя проекта на library-production.

## 6. Изменение окружения после проверки

Штатное обновление действующего стенда:

```bash
cd /opt/library-container
sudo -v
sudo -n make container-update DOCKER=docker CONTAINER_PROJECT=library-production
```

Команда сначала выполняет container-check.
При его ошибке рецепт обновления не запускается.
При успехе создаётся резервная копия, выполняются миграции,
обновляется приложение и проверяется его готовность.

Это изменение действующего стенда с коротким перерывом работы.
Для обычного показа достаточно container-check во временных проектах.

15.10.2026 на library-production подтверждена последовательность:
CONTAINER_CHECK_OK → CONTAINER_UPDATE_OK.

## 7. Завершение работы

Перед длительным перерывом штатно выключить ВМ:

```bash
sudo shutdown -h now
```

Дождаться выключения ВМ, затем переводить ноутбук в сон.
На время защиты отключить автоматический сон ноутбука.

После сна ноутбука наблюдались зависания процессов контейнеров.
Перезагрузка ВМ восстанавливала доступность.
Точная причина не установлена; это не считается устранённой проблемой.

Не удалять volumes и не выполнять docker system prune для восстановления
доступности. Результаты переноса и ограничения отката описаны в
[container-migration.md](container-migration.md).
