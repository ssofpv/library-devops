# Ручная проверка перед защитой

Это сценарий приёмки, а не подтверждение уже выполненной демонстрации.
Проводить на отдельных тестовых данных. Не публиковать пароли на скриншотах.

1. Выполнить `make migrate`, создать пользователя по README, выполнить `make verify`.
2. Запустить `make run`. В приватном окне открыть `/books/`: должен открыться вход.
3. Открыть `/api/books/` без входа: 403. `/health/`: 200 и status=ok.
4. Ввести неверный пароль: сообщение об ошибке, каталог недоступен.
5. Войти с правильным паролем: каталог открывается, в шапке видно имя пользователя.
6. Создать автора, книгу с автором, два филиала и экземпляр; проверить те же записи через API.
7. Проверить фильтрацию по книге и филиалу. Переместить экземпляр во второй филиал;
   книга и инвентарный номер должны сохраниться.
8. Попытаться удалить книгу с экземпляром, занятый филиал и автора с книгой:
   отказ, связанные записи сохраняются; через API — 409.
9. Проверить пустые поля, неверный год, несуществующую ссылку и повторный инвентарный
   номер: ошибки, данные не меняются. Проверить 404 для отсутствующей записи.
10. Удалить экземпляр, затем книгу, автора и пустые тестовые филиалы.
11. Нажать «Выйти». Прямая ссылка на каталог снова требует входа, API возвращает 403.
12. Проверить после перезапуска сохранение данных на отдельной тестовой записи.
13. Показать `git ls-files -- .env .venv db.sqlite3` (пустой вывод),
    `git check-ignore -v .env .venv/ db.sqlite3` (правила исключений).
14. Показать задачу → ветку → коммиты → PR → review → успешный CI → main → тег.
    Для обновления аутентификации использовать новые подтверждения; старый v0.1.0
    не содержит веб-интерфейс и вход.
15. Выполнить контрольное изменение через новую задачу, ветку и PR.
