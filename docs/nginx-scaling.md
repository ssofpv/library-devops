# ЛР4: Nginx, масштабирование и отказоустойчивость

Issue: #79.

## Конфигурация

Дополнительный вариант запускается отдельным файлом compose.scaled.yaml.
Основная конфигурация compose.yaml сохранена.

Сервисы:
- nginx — единственная опубликованная точка HTTP-доступа;
- app1 и app2 — два отдельных контейнера Django/Gunicorn;
- db — общая PostgreSQL с именованным volume postgres_data.

Nginx связан с приложениями внутренней сетью proxy.
Приложения связаны с PostgreSQL внутренней сетью backend.
Порты приложений и БД на хосте не опубликованы.

В ответах приложения присутствует X-App-Instance: app1 или app2.
Идентификатор задаётся через APP_INSTANCE_ID; без переменной
используется имя хоста.

Nginx распределяет запросы методом round-robin.
Настроены max_fails=1, fail_timeout=10s и не более двух попыток
обращения к upstream при предусмотренных ошибках.
Проверка отказа пассивная, по результатам запросов.
Принудительный повтор non_idempotent не включён.

## Ограничения горизонтального масштабирования

1. Локальная SQLite привязана к файлу конкретного экземпляра.
   Независимые копии такого файла не дают общего состояния.
   В контейнерном варианте используется общая PostgreSQL.

2. PostgreSQL остаётся одним узлом. Увеличение числа приложений
   увеличивает число соединений и нагрузку на общую БД.
   Отказ БД затронет оба приложения; репликация и переключение БД
   в этой работе не реализованы.

3. Сессии Django хранятся в общей БД. Для работы входа при переходе
   между экземплярами нужны одинаковый DJANGO_SECRET_KEY
   и общая база сессий. Раздельные БД или разные ключи нарушат
   эту схему. Проверки /health/ сами по себе не проверяют вход.

4. Миграции изменяют общую схему. Их нужно выполнять один раз
   при обновлении, а не одновременно из каждого экземпляра.
   Совместимость схемы со старым и новым кодом требует отдельной оценки.

5. app1 и app2 перечислены явно. Текущая конфигурация рассчитана
   на два экземпляра; автоматического масштабирования нет.
   Для добавления экземпляра нужно изменить Compose и upstream Nginx.

6. Имена upstream разрешаются при загрузке конфигурации Nginx.
   После пересоздания приложения с изменением IP требуется
   обновить разрешение адресов перезагрузкой конфигурации Nginx.
   Проверенный stop/start не заменяет проверку пересоздания.

7. Существующий container_update.sh рассчитан на один сервис app.
   Для дополнительной конфигурации нужен отдельный порядок обновления,
   учитывающий оба приложения, резервную копию и Nginx.
   Использовать старый updater для неё без адаптации нельзя.

8. Все контейнеры работают на одной ВМ с ограниченными CPU и RAM.
   Дополнительные экземпляры делят её ресурсы.
   Единственный Nginx и сама ВМ остаются точками отказа.
   Достаточность ресурсов под нагрузкой не доказана.

Статика собирается в образ и обслуживается WhiteNoise.
При одинаковом образе у экземпляров она одинакова.
В текущих моделях нет пользовательских файловых загрузок;
общее файловое хранилище для них пока не требуется.

## Статус

Дополнительная конфигурация проверена в учебном окружении.
Действующий library-production пока использует прежнюю конфигурацию.
Review, CI, слияние и развёртывание дополнительного варианта
на основном стенде ещё не выполнены.
