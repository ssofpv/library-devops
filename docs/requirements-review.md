# Проверка требований ЛР1 и проекта Библиотека

Проверка выполнена 19.09.2026 по двум приложенным Word-документам, исходному архиву
с Git-историей и тексту задания, переданному в сообщении. Google Docs по ссылке
не открылся; наличие дополнительных требований в недоступных вкладках не проверено.
Исходный HEAD — b6d6956; изменение аутентификации подготовлено отдельно от main.

## Результат

Минимальное приложение соответствует проверенным функциональным требованиям ЛР1
после добавления аутентификации. Для завершения сдачи нужны удалённые Issue/PR,
review второго участника, CI нового изменения и живая демонстрация.
Согласование темы и обновлённого ТЗ подтверждает преподаватель, не исходный код.

## Проверка собственного ТЗ

FR-01–FR-08: CRUD четырёх сущностей, связи, фильтры, формы и предметные ограничения
представлены в коде и автоматических тестах. FR-09: health проверяется без входа.
FR-10 и AC-10 добавлены для аутентификации; AC-01–AC-06 теперь выполняются после входа.
API использует сессии: отказ без аутентификации — 403, а не обещание 401.

Обновлённое ТЗ сохраняет исходную архитектуру. Стандартные auth/session-таблицы
Django уже входят в миграции фреймворка. Менять библиотечные модели и переносить
существующие книги не требуется. При обновлении выполнить make migrate.

ТЗ исключает выдачи, возвраты, читателей и штрафы. В общем описании темы также
упомянуты факультеты, отчёты и использование книг. Для ЛР1 явно разрешён минимальный
объём и требуется ≥3 сущностей; четыре имеющиеся сущности это условие выполняют.
Согласовать с преподавателем, что факультеты/отчёты/выдачи относятся к следующим этапам.
Не следует заявлять, что они уже реализованы.

Команды backup, restore, up, down, container-check приведены в задании как
рекомендуемый общий интерфейс для сквозного проекта. В ЛР1 отдельного обязательного
требования реализовать контейнеризацию, CD, очереди, Nginx и мониторинг нет.
Эти компоненты сейчас отсутствуют и не должны отмечаться выполненными.
Текущие setup/run/test/quality/migrate/verify реализованы; setup требует заранее создать .venv.

## Исправленные несоответствия

- Отсутствовал обязательный вход в рабочее приложение и API.
- README и несколько API/HTML-инструкций сообщали об отсутствии аутентификации.
- API филиалов одновременно утверждал отсутствие экземпляров и описывал их защиту.
- manual-check.md был пустым, хотя на него ссылался README.
- Пользователи и сессии не были описаны в схеме данных.
- Язык Django был en-us; теперь ru, в том числе стандартные сообщения входа и API.
- Word-документы исключали авторизацию; границы уточнены: базовый вход обязателен,
  отдельные роли сотрудников остаются вне объёма.
- В списке источников ТЗ репозиторий назван открытым, а в общих положениях закрытым;
  несогласованное слово «открытом» удалено. Реальная видимость GitHub не проверена.

## Доказательства проверки

До изменений: make verify, 82 теста, Python 3.12.14.
После изменений: make verify, 95 тестов, Python 3.12.14, 3.13.15 и 3.14.7.
На 3.13 и 3.14 отдельно установлены точные зависимости из requirements-dev.txt.
Успешны Ruff, проверка форматирования, Django check, проверка миграций (No changes detected)
и все тесты. Это локальные прогоны, не результаты GitHub Actions.

Проверены: верный/неверный пароль, пустые данные, неактивный пользователь,
потеря доступа после деактивации, все рабочие HTML-маршруты и API CRUD без входа,
доступ обычного пользователя, запрет внешнего next, POST-выход, недействительность
старой сессии после выхода, CSRF входа/выхода/API, хеш пароля и публичный health.
Прежние проверки предметной области не удалялись: в их подготовку добавлена сессия.

CI, Makefile, requirements и конфигурация Ruff не менялись.
`git ls-files -- .env .venv db.sqlite3` — пустой вывод; правила игнорирования найдены.
Это подтверждает исключение этих путей, но не является полным аудитом всей истории на секреты.
Снимки 82 тестов и прежнего CI в отчёте оставлены как исторические; они не доказывают
приёмку новой аутентификации. Для нового PR нужны собственные результаты.

В отчёте отдельно подтверждён review PR №35 (восстановление), но не исходного PR №33.
Для выбранной демонстрационной функции следует показать её собственный review
или использовать новый PR аутентификации с полной цепочкой подтверждений.

## Перед сдачей

1. Применить патч в рабочей ветке по authentication-change.md и добавить обновлённые DOCX.
2. Создать локального пользователя, выполнить make migrate и make verify.
3. Выполнить manual-check.md на компьютере участницы; сохранить снимки входа и отказа доступа.
4. Завершить Issue → PR → review → CI → main. Не выдавать локальный патч за слитый PR.
5. Сохранить v0.1.0 как исторический тег. При необходимости согласовать новый тег
   на коммите после слияния аутентификации; не передвигать старый тег молча.
6. Согласовать дополнение ТЗ и границы факультетов/отчётов; подготовить контрольное изменение.
