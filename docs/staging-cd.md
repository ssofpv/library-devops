## Стенд и доступ

- ВМ library-app, Ubuntu; staging-проект library-staging.
- Адрес приложения: http://192.168.56.10:18000.
- Адрес ВМ в Tailscale: 100.89.219.57.
- Pipeline входит по отдельному SSH-ключу как library-deploy.
- Метка исполнителя Tailscale: tag:library-cd; разрешён только TCP 22 к ВМ.
- Обычный SSH используется поверх сети Tailscale; Tailscale SSH включать не требуется.
- ВМ и компьютер с VirtualBox должны работать во время выпуска.

GitHub Actions использует secrets TS_OAUTH_CLIENT_ID, TS_OAUTH_SECRET,
STAGING_SSH_KEY и STAGING_KNOWN_HOSTS. Последний содержит публичный ключ сервера
с адресом 100.89.219.57. Проверка ключа сервера обязательна.
Приватный SSH-ключ и OAuth secret не добавляются в репозиторий.

## Файлы на сервере

Все файлы в /opt/library-staging принадлежат root. Каталог имеет права 700.
Пользователю library-deploy не предоставляются группа docker и общий sudo.

- compose.staging.yaml и compose.yaml — проверенные конфигурации.
- .env.staging — настройки окружения, права 600.
- .smoke.json — данные входа приложения для приёмки, права 600;
  JSON с полями username и password. Значения вводятся локально на сервере
  и не выводятся в журналы. После смены пароля приложения файл нужно обновить.
- deploy_staging.py и staging_smoke.py — проверенные сценарии, права 644.
- releases/ — закрытые резервные копии и записи выпусков.

Имя проекта остаётся library-staging, том БД — library-staging_postgres_data.
Перенос конфигурационных файлов не создаёт новую базу. Production использует
другие ресурсы и не является целью этих сценариев.

## Установка после review и до слияния

Для PR #102 установка и проверка разрешений уже выполнены. Этот раздел
сохранён для последующих согласованных изменений серверных сценариев.

Полина проверяет workflow, сценарии, тесты и эту инструкцию в PR. Софья
устанавливает именно проверенные версии файлов до merge, потому что первый
push main после merge уже запустит CD. Последующие изменения сценариев также
требуют review и отдельной установки администратором: pipeline не заменяет
код, который запускается с правами root.

В PowerShell Windows из корня проверенной рабочей ветки:

```powershell
scp -i "$env:USERPROFILE\.ssh\library_sofia" -o IdentitiesOnly=yes .\scripts\deploy_staging.py .\scripts\staging_smoke.py sofia@192.168.56.10:/home/sofia/lr6-staging-check/
```

В SSH-сеансе Ubuntu под sofia:

```bash
sudo install -o root -g root -m 644 /home/sofia/lr6-staging-check/deploy_staging.py /home/sofia/lr6-staging-check/staging_smoke.py /opt/library-staging/
```

Через sudo visudo -f /etc/sudoers.d/library-staging-cd добавить правило:

```sudoers
library-deploy ALL=(root) NOPASSWD: /usr/bin/python3 /opt/library-staging/deploy_staging.py *
```

Проверить sudo visudo -c. Сценарий принимает только один полный SHA из
40 строчных шестнадцатеричных символов; произвольные команды, пути, теги и
дополнительные аргументы не принимаются. Сценарии и конфигурация остаются
недоступными для изменения пользователю pipeline.

Перед merge проверить вход по ключу, список разрешений sudo -n -l и полный
пробный запуск сценария на текущем опубликованном SHA. Успех такого запуска
подтверждает серверный сценарий, но не заменяет запуск из GitHub Actions.

## Последовательность выпуска

1. CI выполняет проверки приложения и пять отдельных тестов сценария CD.
2. Только успешный push main публикует проверенный образ с полным SHA.
3. Задание deploy-staging ожидает успешную публикацию, подключает Tailscale
   и запускает по SSH sudo -n /usr/bin/python3 /opt/library-staging/deploy_staging.py SHA.
4. Серверная блокировка не допускает параллельный запуск. В workflow также
   задан concurrency library-staging-deploy с cancel-in-progress: false.
5. Проверяется конфигурация и фиксируется фактически работающий предыдущий образ.
6. Новый образ загружается из GHCR без сборки. Ошибка registry останавливает
   выпуск до замены контейнера.
7. Создаётся pg_dump. Копия восстанавливается в отдельную временную базу,
   запись LR6-001 сравнивается с исходной; временная база затем удаляется.
8. Проверяется отсутствие неприменённых миграций командой migrate --check.
9. Обновляется только приложение: up --no-deps --no-build --pull never --wait.
   База не пересоздаётся; ожидание healthcheck ограничено 180 секундами.
10. Через HTTP проверяются health, точное совпадение version с SHA, реальный
    вход по паролю и строка LR6-001 с ожидаемыми книгой, филиалом и статусом.
11. Только после приёмки обновляются APP_IMAGE_TAG и releases/last-success.json.
    В release.json сохраняются requested_sha, previous_image, backup и status.

Любая ошибка приводит к ненулевому коду завершения и ошибке задания GitHub.
После замены контейнера неуспешный образ может остаться запущенным; автоматический
откат не реализован. Администратор выполняет ручной возврат и проверяет результат.

## Ограничения и ручной возврат

Сценарий не применяет новые миграции. Для выпуска с изменением схемы сначала
нужен проверенный план обновления и восстановления данных. Возврат образа
сам по себе не откатывает схему или данные PostgreSQL.

Проверенная версия для ручного возврата:
56e6adeaf3a8108799f5f1b6e67903fe4cf5f15b. Возврат на неё после неуспешных
healthcheck и пользовательской приёмки выполнен успешно. Команда на ВМ:

```bash
sudo /usr/bin/python3 /opt/library-staging/deploy_staging.py 56e6adeaf3a8108799f5f1b6e67903fe4cf5f15b
```

Для следующих выпусков брать previous_image из записи соответствующего выпуска.
Сценарий принимает SHA после двоеточия. Ручной возврат использует те же проверки,
резервное копирование и блокировку. После него проверить вход и LR6-001 также
через браузер и сохранить доказательства.

После эксперимента возврата актуальная версия восстановлена командой:

```bash
sudo -u library-deploy sudo -n /usr/bin/python3 /opt/library-staging/deploy_staging.py 66e0572d90faf390ce4061361c4b5c3ce27a4747
```

Образ 7316fc27720b1e7fb5149e5fb95b9ca15c07c32f не имеет /version/ и не проходит
приёмку данным сценарием. Для экспериментов CD базовой версией служит 56e6ade…
или более поздняя уже принятая версия с /version/.

Автоматический пользовательский сценарий проверяет вход и чтение экземпляра.
Создание и изменение записей этим сценарием не проверяются.

Локально: make verify; python scripts/test_deploy_staging.py; git diff --check.

Локально make verify завершился успешно: 128 тестов приложения, покрытие строк
99% с округлением; пять тестов сценария CD также прошли. Процент относится к
измеренным строкам приложения, а не к доле выполненных требований лабораторной.

Actions №193 подтвердил автоматический успешный выпуск через GitHub Actions.
Ответ /version/ совпал с requested_sha в releases/last-success.json,
status был accepted; предыдущий образ и путь database.dump сохранены.

Отрицательные эксперименты выполнены вручную на стенде через установленный
серверный сценарий CD. Отдельные неуспешные задания GitHub Actions для этих

Временные изменения env и Compose восстанавливались обработчиком EXIT.
В тесте страницы менялся шаблон, а не записи базы. После восстановления
файлов выполнялось повторное развёртывание, чтобы убрать тестовые параметры
из реально запущенного контейнера. После всех экспериментов 66e0572… принята,
LR6-001 проверен через браузер; книга, филиал и статус сохранились.

Серверная блокировка проверена экспериментом. Ограничение concurrency в workflow
подтверждено конфигурацией; два одновременно запущенных задания GitHub отдельно
не моделировались.

## Исправление DNS на стенде

При первом серверном запуске загрузка из GHCR остановилась на DNS-ошибке.
Изменения контейнера не начались. Запрос через основной интерфейс enp0s3 также
завершался Network is unreachable; после замены DNS имя ghcr.io определилось.
Причина не приписывается Tailscale: отказ воспроизводился через enp0s3.

Перед изменением выполнена копия /etc/netplan в /root/netplan-before-lr6-dns-….
В /etc/netplan/99-z-library-dns.yaml записана конфигурация:

```yaml
network:
  version: 2
  ethernets:
    enp0s3:
      dhcp4: true
      dhcp4-overrides:
        use-dns: false
      nameservers:
        addresses: [1.1.1.1, 8.8.8.8]
```

netplan generate прошёл. При повторном netplan try --timeout 120 настройки
подтверждены Enter, получено Configuration accepted. DNS-разрешение и загрузка
образа после применения проверены. Отдельная проверка после перезагрузки
в рамках этого этапа не проводилась.
